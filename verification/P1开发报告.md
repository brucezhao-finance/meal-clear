## 2. 设计决策

### 2.1 50 人同质组算法
- 【事实】`MAX_PEOPLE = 50`，是你明确要求的上限（原方案是 6）。
- 【事实】≤6 人沿用 P0 的逐人 beam，输出由 `test_p0_regression.py` 哈希锁定，防止回归；>6 人走新路径。
- 【事实】做法：硬要求与偏好**完全相同**的人归为一个同质组（`group_key`，组编号 G1… 按首次出现顺序）。组内可选餐品和偏好得分一致，所以每组只做一次硬要求核对，把“整组吃什么”表示成多重集合（餐品 × 数量）。
- 【事实】搜索限制：组内最多 2 种不同套餐（`GROUP_MAX_DISTINCT_OFFERS`），每组只保留前 48 种分配（`GROUP_ALLOCATIONS_CAP`），组间沿用 beam 合并。这些限制会写入 `checked.statement`，所以排名是“已检查范围内的排名”，**不是全局最优**。
- 【事实】请求载荷把相同商品合并成 `quantity=n`；报告 ≥13 人时紧凑展示，`--detail` 展开逐人。
- 【事实】旧 beam 本来就不慢，新算法的价值是候选多样性、可解释的整组分配、载荷合并和紧凑报告，不是提速。
- 【推测】硬要求/偏好各不相同的 50 个人（S50c）会退化为逐人扩展，质量与旧 beam 相当，没有额外收益。

### 2.2 摘要指纹（digest）字段集合
- 【事实】digest = 对材料做规范化 JSON 后取 SHA-256（64 位十六进制）。材料字段集合固定为 10 项，多或少都会被 `assert_material_clean` 拦截：
  `v`（DIGEST_VERSION=1）、`store_code`、`fulfillment`、`need_tableware`、`lines`、`take_way`、`total_cents`、`fee_breakdown`、`claim_coupons`、`quote_window`。
- 【事实】`lines` 含套餐 id、名称、商品编码、数量、券标题；`claim_coupons` 按名称和标签排序，保证同输入同摘要；`quote_window` 含报价时间和过期时间。
- 【事实】**不进 digest**：谁吃哪份、方案来源（展示信息，同 digest 复用时只刷新展示）。外送只存地址序号和标签，不存地址文本、手机号，材料中出现 `http` 或手机号形态会被拒绝。
- 【事实】`basket_key` 另算：只含门店、履约方式、商品行，用于“同篮子防重复”，防止换个摘要绕过去重。
- 【建议】quote_window 进了 digest，意味着同一方案隔几分钟重新生成摘要就会得到不同 digest。这是有意为之（旧确认不可复用），但操作上要告诉用户别拿旧编号去确认。

### 2.3 TTL
- 【事实】摘要默认有效 600 秒（`SUMMARY_TTL_SECONDS`），`--ttl-seconds` 可调，范围 60–1800 秒。
- 【事实】过期后执行返回退出码 3，须重新生成摘要并重新确认。
- 【事实】同篮子防重复窗口 24 小时（`DUPLICATE_BASKET_WINDOW_SECONDS`）；`pending` 超过 600 秒仅改变提示措辞。
- 【推测】600 秒是否够真实用户核对一份 50 人订单，没有验证；摘要太长时可能偏紧。

### 2.4 三重门
执行领券/下单必须同时满足，缺一不可（`gate.py`、`net_guard.py`，07 图）：
1. 显式 `--execute`（默认是预演，零写入）。
2. `--confirm-digest` 为完整 64 位摘要编号，与账本记录匹配且未过期。
3. 写目标是回环地址：仅 `127.0.0.1` 和 `[::1]`。

- 【事实】审查抽查了 18 种主机写法（`localhost`、`127.1`、`0.0.0.0`、十进制/八进制 IP、尾点域名、`[::ffff:127.0.0.1]`、带 userinfo 等），全部被拒。
- 【事实】官方端点在读取 Token 和 initialize **之前**就被拒（退出码 4），测试对 `McpClient`、`initialize`、`urlopen` 打桩为遇到即失败。
- 【事实】写工具只允许 `auto-bind-coupons` 与 `create-order`；其余写工具（取消订单、新建地址、抽奖等）永久拒绝；`call()` 白名单只含 12 个只读工具；代码里没有 `--endpoint` 参数，环境变量只读 `MCD_MCP_TOKEN`。

### 2.5 账本格式与崩溃恢复
- 【事实】位置 `<repo>/local-state/orders/`，文件按完整 64 位 digest 命名，目录 0700、文件 0600，`O_NOFOLLOW`，单文件上限 1,000,000 字节，schema 为 `meal-clear/ledger/1`。
- 【事实】内容只存事件名、步骤状态、数字错误码和时间；不存参数、回包、券码、地址或支付链接。
- 【事实】步骤状态（`config.py` 唯一定义）：
  - claim：`none / not_required / pending / succeeded / failed / unknown`
  - requote：`none / consistent / changed / error`
  - order：`none / pending / created / failed / unknown`
- 【事实】写入方式：`flock` 互斥，临时文件 + `fsync` + `os.replace` + 目录 `fsync`。
- 【事实】**先落账再写请求**（write-ahead）：`place_execute` 顺序为预检 → 回环校验 → 工具校验 → 新鲜度 → WriteGate → `begin_step`（`pending` 落盘）→ 调用 → 分类落账。
- 【事实】崩溃恢复：进程在调用中途死掉会留下 `pending`；下次读取时若 owner 锁可取得（持有者已退出），就地改为 `unknown` 并追加 `recovered_from_pending` 事件。另一进程仍持有锁时保持 `pending`。
- 【事实】`unknown` 状态（超时、缺 orderId、异常结构、未预期异常）一律退出码 6，**不自动重试**（写路径只尝试 1 次）。同 digest 只有状态为 `none` 才能开始该步骤，否则退出码 5。
- 【建议】遇到 `unknown`，先看 App 订单列表再决定；不要用 `--allow-duplicate-basket` 去试。

## 3. 四个命令用法与退出码

所有命令默认是预演。真正写入必须加 `--execute --confirm-digest <完整64位>`，且目标是回环地址。

```text
order-summary --request <schema_version=2 请求> [--signature 前缀 | --rank N]
              [--take-way N] [--skip-claim] [--ttl-seconds 60-1800]
              [--city X --keyword Y] [--detail] [--save 文件] [--json]
order-claim   --digest <≥12位前缀> [--execute --confirm-digest <64位>] [--json]
order-place   --digest <≥12位前缀> [--execute --confirm-digest <64位>]
              [--allow-duplicate-basket] [--json]
order-status  (--digest <前缀> | --order-id <订单号>) [--json]
```

- `order-summary`：选方案 → 重建 → 重新核价 → 读将领券集合 → 生成摘要与 digest → 写账本。不写任何服务端数据。
- `order-claim`：预演只说明“将调用 auto-bind-coupons，本次未调用”。执行后重新查券、重新核价；价格或内容变化则生成新摘要，旧摘要失效。领券是一键领全部，不能逐张选、不可撤销（你已同意）。
- `order-place`：预演会显示“当前不能下单：请先完成领券”等前置缺口。执行后创建待支付订单，不自动付款；订单号只在本次输出显示。
- `order-status`：优先读本地账本，有订单号才联网查询。

退出码（`SKILL.md` 同款）：

| 码 | 含义 |
|---|---|
| 0 | 成功或预演完成 |
| 1 | 输入、认证或协议错误 |
| 2 | 没有可确认的方案 |
| 3 | 需要重新确认（过期、价格/内容变化、超预算、需选取餐方式、已生成新摘要） |
| 4 | 安全门或前置条件拒绝，未发出写请求（含官方端点被拒） |
| 5 | 重复执行被拒 |
| 6 | 写调用结果未知，禁止重试 |

## 5. 50 人性能数字

来源：`性能记录.md`（`python3 tests/bench_scale.py`，合成数据，Python 3.9.6，Darwin arm64，5 次中位数）。

- 【事实】默认参数（`per_person_top_k=8`，`max_whole_candidates=200`）：最慢 S50b（16 个同质组）引擎约 406 ms；S50a 62 ms；S50c 145 ms。
- 【事实】上限参数（`per_person_top_k=12`，`max_whole_candidates=1000`）：S50b 约 2.94 s，S50c 1.82 s，S50a 442 ms。目标是 <10 s，均达标。
- 【事实】不利情形：S50b 默认参数下新路径约 450 ms，旧 beam 约 233 ms，慢约 2 倍，原因是每组要枚举并排序最多 48 种拆分。未调参，因为绝对耗时远低于目标。
- 【事实】模拟服务上 50 人 `live-plan`：`calculate-price` 12 次（等于默认 `max_quotes`），工具调用 24 次，远低于单次运行上限 150，未触发限流等待，墙钟 0.08–0.11 s。
- 【推测】真实网络下耗时会明显更长，且真实官方 `calculate-price` 对 `quantity=n` 合并的 50 人数量是否接受、是否限额，没有验证。

## 7. 未验证项（强调：全部需要你在真实 Token 下验证）

以下没有任何真实环境证据。模拟服务按我对协议的理解写成，**模拟通过不能证明真实服务行为相同**。

1. 真实 `auto-bind-coupons` 的行为：是否真的一键领全部、能否部分失败、返回结构是否与模拟一致、是否有当日次数限制。
2. 真实 `create-order` 的行为：返回字段（订单号、支付信息）与模拟是否一致；是否真的只创建待支付订单、不自动扣款；超时后是否可能已建单。
3. `calculate-price` 是否会**自动套用最优券**：这决定领券前后价格是否会变。模拟里的 +¥3.00 是人为构造的场景，真实是否出现、方向如何，未知。
4. 领券后价格变化：真实情况下，领券后重新核价是变低、不变，还是因券门槛变高，未知。
5. 订单可否取消：代码永久拒绝取消订单，也就是说如果误下单，**只能你在 App 里处理**。官方是否允许取消待支付订单、多久自动关闭，我没有验证。
6. 外送与得来速在真实账号上的可用性：外送依赖已有地址（本工具不新建地址）和可配送门店；得来速的取餐方式编码、门店支持情况，均只在模拟里验证。
7. 50 人合并数量（`quantity=n`）在真实 `calculate-price` 和 `create-order` 上的行为与限额。
8. 团餐、人均预算类能力尚未做（按你的决定放最后）。
9. 3 人场景 ¥70.00 的独立手算、非回环拒绝并入 e2e：见 4 节。

## 8. P2 前置条件与建议的真实验证步骤

前置条件（【建议】）
- 你本人持有的有效 Token，只通过 `MCD_MCP_TOKEN` 环境变量或受控 token 文件提供，不要写进仓库。
- P2 需要决定如何放开官方端点的写操作：当前是代码层恒定拒绝。放开前应有单独开关和你的明确确认，且仍保留三重门、账本和写工具白名单。
- 把本报告第 7 节逐条转成真实验证清单，每条给出“预期”和“实际”两栏，不预设模拟结果成立。
- 先看审查的非阻断建议：把非回环拒绝并入 `e2e_order_flow.py`；`test_sim_write_tools.py:308` 的 `/Users/` 字面量改成拼接构造；`mcp.py` 的 `_write_ctx` 是实例级可变状态，若以后并发使用需改成调用级参数。

建议的真实验证顺序（由低风险到高风险）
1. 只读：`order-summary` 用 `--skip-claim` 对真实账号生成摘要，核对价格、门店、取餐方式与 App 显示一致。不领券、不下单。
2. 只读：`calculate-price` 看是否自动套用最优券，对照 App 手动结算页金额。
3. 领券：选一张你本来就打算用的券场景，`order-claim` 先预演，再 `--execute`。核对 App 里领到的券是否与摘要“将领券集合”一致，领券后价格如何变化。
4. 下单：用**最小金额**的测试订单（单个低价商品、单人、到店），`order-place --execute`，核对：待支付状态、订单号、是否自动扣款、能否在 App 中取消。验证完立刻取消。
5. 重复保护：对同一 digest 再执行一次，应得到退出码 5，且 App 里没有第二笔订单。
6. 之后才依次验证外送、得来速、多人，最后才是 50 人。
7. 全程保留账本和输出，出现 `unknown`（退出码 6）时先去 App 订单列表核实，不要重试。

## 9. 已知限制

- 【事实】账本依赖 `fcntl`/`flock`，**仅支持 POSIX**（macOS、Linux）。无 `fcntl` 的平台账本不可用，写操作会被拒绝。
- 【事实】**跨进程限流不共享**：限流器是进程内的（500 次/60 秒），同时开多个进程各自计数，合计可能超过。单次运行另有 150 次工具调用上限。
- 【事实】`_write_ctx` 是客户端实例级状态，非线程安全；当前 CLI 单线程，且写前有账本 flock 串行，未构成现实风险。
- 【事实】排名只在已检查范围内，不是全局最优；搜索限制已写入报告。
- 【事实】不保证“全网最低价”，文档只在否定句里提到。
- 【事实】同一用户机器上账本只防“本机重复”。你在手机 App 或另一台机器上下的单，账本看不到。
- 【推测】`pending` 超过 600 秒仍可能是调用确实还在进行（只改提示措辞），不应据此直接判定失败。
- 【事实】审查未重跑全量测试，依赖实现步记录的证据；本报告同样未重跑。
