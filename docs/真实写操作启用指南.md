# 真实写操作启用指南（默认关闭，未经真实验证）

本指南写给**项目所有者本人**：怎样在自己的终端里，小心地打开官方端点上的领券和下单，并在出问题时紧急关闭。

**先看现状：** 真实领券/下单的代码路径已经具备，但**默认关闭，也从未用真实账户验证过**。本机自动测试只用回环模拟服务和网络桩，证明的是“门控和参数构造按设计工作”，不证明官方接口的真实返回、部分成功或超时后的真实状态。所以第一次真实测试请当作实验：金额从最小开始，每一步你自己看、自己输入。

**Agent 不得代做：** 不得替你在终端确认，不得用 pty、管道、expect、script 或重定向绕过终端检查，不得向你索要 Token，不得替你设置开关、编辑 `real-write.json` 或 `WRITE_LOCK`，不得代跑 `order-resolve` 和 `write-lock --off`。Agent 只能生成订单摘要，并提示你“请在你自己的终端运行并亲手确认”。

## 1. 四道门

官方写请求要同时通过四道门，任何一道不过，都不会发出请求：

| 门 | 条件 |
| --- | --- |
| 1 | 命令带 `--execute` |
| 2 | `--confirm-digest` 是完整 64 位摘要编号，与账本记录匹配且未过期（默认 600 秒） |
| 3 | 写目标固定：回环地址（模拟）或官方端点 `https://mcp.mcd.cn`（字符串严格相等，无参数可改） |
| 4 | 真实写开关已打开 + 紧急锁未锁 + stdin/stdout 都是终端并亲手输入确认短语 + 金额与次数未超上限 |

第 4 道门**默认关闭**。其余写工具（取消订单、新建地址、抽奖、积分商城下单、派对/活动预约 `party-order-create`、支付、买卡、兑换）在任何情况下都被拒绝。团餐没有独立下单工具，走 `create-order`（`beType=6`），其官方端点真实下单一律被代码拒绝。

## 2. 前置条件

- 阶段 A–C（Token 连通、真实只读查询、业务假设）已完成并记录，见你本地的《真实测试清单》。
- 你有可用的麦当劳 MCP Token，并且只放在自己终端的环境变量 `MCD_MCP_TOKEN` 里，或放在固定凭证文件 `local-state/credentials/mcd_mcp_token`（目录权限 700，文件权限 600，不得是符号链接）。写命令**不接受**任意 `--token-file` 路径。
- 你知道怎样在麦当劳 App 里查看和取消待支付订单：本工具不会付款，也不会取消订单，误下单只能你在 App 里处理。
- 系统是 macOS 或其他 POSIX 系统（账本锁依赖 `fcntl`）。

## 3. 启用步骤

1. 在自己的终端里进入项目目录。
2. 创建本地状态目录并收紧权限：
   ```bash
   mkdir -p local-state && chmod 700 local-state
   ```
3. 打开开关，二选一：
   - 仅当前终端会话：`export MEAL_CLEAR_ENABLE_REAL_WRITE=1`（值必须恰为 `1`）。
   - 或写配置文件 `local-state/real-write.json`，然后 `chmod 600 local-state/real-write.json`：
   ```json
   {
     "enabled": true,
     "max_order_cents": 3000,
     "max_orders_24h": 1,
     "max_claims_24h": 1
   }
   ```
4. 配置文件必须是你自己的普通文件（不能是符号链接，不超过 64KB，只允许上表的四个键）；写错、越界或权限不对都会被拒绝，不会被悄悄修正。
5. 首次使用前，先演练紧急关闭：`python3 scripts/meal_clear.py write-lock --on`，再 `write-lock --off`（见第 6 节）。

### 上限表

| 配置项 | 含义 | 默认 | 硬上限 |
| --- | --- | --- | --- |
| `max_order_cents` | 单笔订单应付金额，单位分 | 10000（¥100） | 50000（¥500） |
| `max_orders_24h` | 24 小时内本机账本中的官方下单次数 | 3 | 10 |
| `max_claims_24h` | 24 小时内本机账本中的官方领券次数 | 1 | 3 |

超过硬上限的配置会被拒绝（不会截断）。上限只统计本机账本，你在手机 App 或其他机器上的操作不计入。

## 4. 人工确认怎么输入

官方路径执行时，程序会在终端打印要点，然后要求你**逐字输入**一句话，只给一次机会：

- 领券：`<摘要编号末 6 位> 确认领券`
- 下单：`<摘要编号末 6 位> 确认下单`

短语绑定当次摘要和步骤，领券的短语不能用于下单。多一个空格、大小写不同或输入旧短语都会被拒绝。官方路径要求 stdin 和 stdout 都是终端，所以不能管道输入，也不能把输出重定向到文件。

## 5. 与《真实测试清单》阶段 D/E 的命令对照

| 清单项 | 命令 / 行为 | 说明 |
| --- | --- | --- |
| D1–D3 | `order-summary`、`order-claim --digest 前缀`（预演） | 只读，不需要开关 |
| D4 | 打开开关后：`order-claim --digest 前缀 --execute --confirm-digest 完整64位`，按提示输入 `<末6位> 确认领券` | 四道门；领券前先重新核价 |
| D5 | 领券后自动重新查券、核价 | 价格变化返回退出码 3，并给出新摘要，需你重新确认 |
| D6 | 对同一摘要再次 `--execute` | 退出码 5，不调用 |
| D7 | 观察返回 | 账本只记数字码和通道；返回结构异常按结果未知处理 |
| E1–E3 | 下单预演；摘要过期；错误摘要编号 | 预演只读；过期退出码 3；编号错退出码 4 |
| E4 | `order-place --digest 前缀 --execute --confirm-digest 完整64位`，输入 `<末6位> 确认下单` | 成功只表示创建了**待支付订单**，付款由你在 App 完成 |
| E5 | `order-status --digest 前缀` | 订单号打码 |
| E6 | 同一摘要再次 `--execute` | 退出码 5 |
| E7 | 在 App 里取消待支付订单 | 本工具永不取消 |
| E8 | 断网后执行 | 退出码 6，不自动重试，该篮子锁定 24 小时，见第 7 节 |
| E9–E11 | 外送 / 得来速 / 3 人订单 | 参数构造与模拟共用同一段代码；真实映射是否正确待你核对 |
| E12 | 换新摘要但商品相同 | 同篮子守卫退出码 5；有未解决的结果未知时为 8 |

## 6. 紧急关闭与解除

```bash
python3 scripts/meal_clear.py write-lock --status   # 查看
python3 scripts/meal_clear.py write-lock --on       # 立即锁定，所有官方写一律退出码 8
python3 scripts/meal_clear.py write-lock --off      # 解除，须在终端输入「确认解除写锁」
```

`--on` 和 `--status` 不需要终端确认。`WRITE_LOCK` 以任何形态存在（文件、目录、符号链接）都视为已锁定。关闭开关（取消环境变量或把 `enabled` 改回 `false`）同样会让官方写回到退出码 4。

## 7. 结果未知怎么办

退出码 6 表示请求可能已经到达官方，但结果不明（超时、断连、3xx 重定向等）。工具**不会重试**，并把该篮子锁定 24 小时（之后同篮子新摘要返回 8）。

1. 先运行 `order-status --digest 前缀`，再到麦当劳 App 的订单列表或券包里核实到底有没有订单或券。
2. 核实后在自己的终端人工标注：
   ```bash
   python3 scripts/meal_clear.py order-resolve --digest 前缀 --step order --as created        # 或 not-created
   python3 scripts/meal_clear.py order-resolve --digest 前缀 --step claim --as claimed        # 或 not-claimed
   ```
   需要终端输入 `<末6位> 确认标注`。标注是你的人工声明，工具不会去官方核实，写错会让账本与现实不一致；事件会留痕，但不会写入订单号。
3. 标为 `not-created` / `not-claimed` 后不再计入次数并解除篮子锁；标为已创建 / 已领取则继续计入。

## 8. 回退方式

- 想马上停止：`write-lock --on`，并取消环境变量或把 `enabled` 改回 `false`。
- 误下单：只能在麦当劳 App 里取消待支付订单，本工具不提供取消。
- 误领券：领券不可撤销，也无法逐张选择。

## 9. 已知限制（请如实对待）

- **终端检查无法区分“真人”和“被程序驱动的伪终端”。** 它只能证明当前有交互终端。能分配 pty 的程序（例如 Agent、`script`、`expect`）在技术上可能绕过它。实际防线是：规则禁止 Agent 代为确认、开关由你自己打开、短语要看屏幕才能输入、金额与次数上限、紧急锁。不要把它当成“技术上无法绕过”。
- 官方 `create-order`、`auto-bind-coupons` 的真实返回结构、是否部分成功、重定向或超时后是否已经建单，都**没有真实证据**；程序对 3xx 一律按结果未知处理。
- 金额上限使用重新核价后的应付额；若官方实际扣款额与核价不同，只会在结果里报告，无法事前阻止。
- 次数和金额上限只覆盖本机账本。
- 次数上限、重复保护和篮子 unknown 锁都依赖本机账本：删除或替换账本目录会重置计数与锁（账本记录被改坏则会拒绝执行，不会放行）。请不要手工删除 `local-state/` 下的账本。
- 确认提示期间在另一终端执行 `write-lock --on` 或关闭开关会生效：写前落账之前会重检，请求不会发出。
- 开关关闭时的提示语仍写“计划在 P2 由用户亲自验证后启用”，含义是：真实写默认关闭，需要你自己启用并自行验证。
- 团餐真实领券/下单未开放：官方端点上团餐（beType=6）的 `--execute` 被代码拒绝（退出码 4），打开真实写开关也不会放行。
